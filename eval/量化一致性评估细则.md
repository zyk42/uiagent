# 量化前后模型一致性评估细则（Function Call 判定标准）

> 配套文档：`README.md`（评估集说明）、`量化模型评估方案.md`（流程与指标总览）
> 本文档回答一个核心问题：**两个模型的输出，怎么算"一致"，怎么算"不一致"**。
> 判定原则：**以 PC-Agent 框架的执行语义为准**——两个 Action 字符串，
> 经过 PC-Agent `run.py` 的解析分发后，是否产生**相同的屏幕操作效果**。

---

## 1. 判定对象

PC-Agent 的输出是伪 function call：JSON 中的 `Action` 字段（字符串），如
`Tap (163, 271)`、`Type (48, 290), ("hello")`、`Shortcut (ctrl, v)`。
评估时**只以 Action 字段作为一致性判定对象**；Thought/Summary 是自由文本，
不作为一致性判据（可选做辅助相似度分析，见 §7）。

## 2. 一致性分级

从严到宽分 4 级，逐级放宽。报告时给出各级比例，**L0/L1 是核心结论，L2 用于定位漂移类型**：

| 级别 | 名称 | 定义 | 用途 |
|---|---|---|---|
| **L0** | 完全一致 | Action 字符串经规范化后**完全相等**（动词+全部参数） | ★ 核心指标（对应方案文档的 Action 完全一致率） |
| **L1** | 执行等价 | 按 PC-Agent 执行语义判定为**同一操作**（参数数值化/集合化后相等，坐标允许微小容差） | 量化漂移的容忍视角 |
| **L2** | 类型一致 | 仅动作**动词**相同，参数不同 | 区分"决策没变、参数变了"与"决策变了" |
| **L3** | 不一致 | 动词不同，或输出无法解析 | 真正的行为漂移 |

**一票否决项（直接判 L3）**：
- 输出不是合法 JSON / 缺少 Thought/Action/Summary 任一字段（计入"JSON 可解析率"，同时判 L3）
- Action 为空、为自然语言句子（无法提取动词与参数）

## 3. 字符串规范化（判定前处理）

两个 Action 字符串比较前，先做统一规范化（否则引号/空格差异会造成大量假不一致）：

| 规则 | 处理 | 理由（真实数据中出现的情况） |
|---|---|---|
| 大小写 | 动词与按键名统一小写比较 | `Press (Enter)` vs `Press (enter)` |
| 引号 | 单双引号等价 | `Type (510, 440), ('Scatter Chart')` vs `("Scatter Chart")`（蒸馏数据中实测存在） |
| 空白 | 连续空格/换行折叠为单空格，首尾 strip | `Tap (163,  271)` |
| 键名别名 | `cmd`→`command`，`ctrl`/`control` 统一，`return`→`enter`，`esc`→`escape` | PC-Agent `shortcut()` 把 command/ctrl 映射到平台键；蒸馏数据实测模型会输出 `cmd` |
| 坐标数值化 | `(163.0, 271)`→`(163, 271)`；非整数字符串按 PC-Agent 行为处理（`int()` 解析失败 → 该步执行失败 → 判 L3 并记格式错误） | PC-Agent `run.py` 用 `int()` 解析坐标 |

注意：**PC-Agent 解析动作名用的是子串包含**（`elif "Tap" in action:`，且先匹配
Double/Triple Tap 再匹配 Tap），所以 `Double Tap` 不会被误判为 `Tap`；
但 `Tap (163, 271) something else` 这类带尾巴的字符串仍能被执行——规范化时**只提取
`动词 (参数...)` 的最长合法前缀**，尾巴忽略并记一条 format_warning。

## 4. 分动作类型的判定标准

PC-Agent 动作空间共 12+4（扩展）个动作，逐个定义 L0/L1 判据。
（"坐标相等"在 L0 下指整数完全相等；L1 下允许容差，见 §4.2。）

### 4.1 逐动作规则

| 动作 | L0（完全一致） | L1（执行等价） | 备注 |
|---|---|---|---|
| `Tap (x, y)` | 坐标完全相等 | 坐标欧氏距离 ≤ **ε_click** | PC-Agent → `pynput` 左键单击 |
| `Double Tap / Triple Tap / Right Tap (x, y)` | 同上 | 同上 | 动词必须相同（单击≠双击，执行效果不同） |
| `Type (x, y), (text)` | 坐标相等 **且** text 规范化后相等 | 坐标距离 ≤ ε_click **且** text 相等 | text 大小写敏感（输入内容就是区分大小写的）；PC-Agent 会自动补回车，两边一致 |
| `Shortcut (k1, k2)` | 键名规范化后**有序**相等 | 键名**集合**相等（修饰键集合相同即可） | PC-Agent 顺序按下 key1/key2，`(ctrl, c)` 与 `(c, ctrl)` 机械行为不同，但 GUI 效果通常等价——故 L1 放宽为集合比较 |
| `Press (key)` / `Press (key) [xN]` | 键名规范化相等（含次数 N） | 同左 | N 不同 → 效果不同（按 1 次 vs 8 次 backspace），判不一致 |
| `Drag (x1, y1), (x2, y2)` | 两个坐标对分别相等 | 起点、终点距离分别 ≤ ε_drag | PC-Agent → `mouseDown`+`moveTo`+`mouseUp` |
| `Scroll (x, y), (n)` / `HScroll` | 坐标相等且 n 相等 | **方向（n 的符号）相同** 且坐标距离 ≤ ε_click；幅度差 ≤ 50% | 滚动是增量操作，方向错=完全反向，幅度差异可容忍 |
| `Stop` | 字符串相等 | 同左 | 无参数 |
| `Tell ({'k': 'v', ...})` | dict 完全相等（`ast.literal_eval` 后比较） | dict 的 **key 集合相等** 且值规范化后相等 | 子任务间传参，key 错=后续子任务取不到参数 |
| `Select (content)` | content 规范化后相等 | content 相等（大小写不敏感） | 语义选区，容差从宽 |
| `Replace (x, y), (text)` / `Append (x, y), (text)` | 坐标相等且 text 相等 | 坐标距离 ≤ ε_click 且 text 相等 | 同 Type |
| `Wait (...)`（扩展） | 时长数值相等 | 时长差 ≤ 1s | |

### 4.2 坐标容差 ε 的取值（L1 用）

坐标是 [0,999] 归一化空间。容差依据：**PC 平台上一个可点击控件（按钮/图标/菜单项）
的典型尺寸约为屏幕短边的 1%~3%**，映射到归一化空间即 10~30：

| 参数 | 取值 | 依据 |
|---|---|---|
| ε_click | **10**（≈1% 屏幕尺寸） | 落在同一控件内的概率极高；1920×1080 屏幕下约 19×11 像素 |
| ε_drag | **20** | 拖拽起止点本身精度要求低于点击 |
| 参考：GT 标注噪声 | 实测 BF16 vs 人工 GT 的坐标距离中位数 ~10-30 | 容差不小于标注噪声水平才有意义 |

> 建议同时报告 ε=0（即 L0）、ε=10、ε=30 三档的坐标一致率曲线，避免单一阈值的主观性。

### 4.3 坐标距离指标（补充统计，非判定）

对**动词一致（L2 及以上）且都带坐标**的样本对，计算归一化欧氏距离
`dist = sqrt((x1-x2)² + (y1-y2)²)`，报告：
- 中位数、p90、max
- 分布直方图（0 / (0,10] / (10,30] / (30,100] / >100 五档）

距离为 0 的占比应等于 L0 坐标一致率，可与 §4.2 互相校验。

## 5. 判定流程（伪代码）

```python
def compare_actions(ref: str, model: str) -> dict:
    # 0. 解析
    a = parse_action(ref)     # -> (verb, params) or PARSE_FAIL
    b = parse_action(model)
    if a is PARSE_FAIL:
        return {"level": "SKIP", "reason": "ref_unparseable"}   # ref 本身坏，剔除该样本
    if b is PARSE_FAIL:
        return {"level": "L3", "reason": "model_unparseable"}   # 量化破坏了格式

    # 1. L0：规范化后完全相等
    if normalize(a) == normalize(b):
        return {"level": "L0"}

    # 2. L1：执行等价（按 §4.1 逐动作规则）
    if a.verb == b.verb and params_equivalent(a, b, eps=EPS):
        return {"level": "L1"}

    # 3. L2：仅动词一致
    if a.verb == b.verb:
        return {"level": "L2", "param_diff": diff_detail(a, b)}

    # 4. L3
    return {"level": "L3", "verb_ref": a.verb, "verb_model": b.verb}
```

整体指标（在 360 条上聚合，并按 平台 × 动作类型 分层）：

| 指标 | 公式 | 解读 |
|---|---|---|
| JSON 可解析率 | parse_ok / 360 | 量化是否破坏输出格式（门槛指标） |
| **L0 完全一致率** | #(L0) / #(ref 可解析) | ★ 核心：行为零漂移比例 |
| L1 执行等价率 | #(L0+L1) / #(ref 可解析) | 放宽容差后的实操等价比例 |
| L2 决策一致率 | #(L0+L1+L2) / #(ref 可解析) | 决策（动词）没变，只是参数漂移 |
| 参数漂移分解 | L2 中按 坐标/文本/按键 分类计数 | 定位量化损伤的部位 |
| 动词漂移矩阵 | L3 的 (ref动词 → model动词) 混淆表 | 定位决策层的漂移模式 |
| 坐标距离中位/p90 | §4.3 | 定位精度漂移的连续度量 |

## 6. 合格线建议与自检

1. **管线自检**：BF16 原版重跑（temperature=0）必须 L0=100%。
   达不到说明 prompt/图片/解析有 bug，修复前不测量化模型。
2. **合格线建议**：
   - JSON 可解析率 ≥ 99%（低于此值说明量化已破坏格式遵循能力）
   - L0 ≥ 55%（参照已有一次实测结果 56.94% 作为当前基线；W4A16 等激进方案若 <50% 需警惕）
   - L1 ≥ L0 + 15pp 且 L2 ≥ 90%（决策层不应有大漂移；若 L2 明显 <90% 说明量化损伤了规划能力而不只是坐标精度）
3. **分层检查**：若某平台/某动作类型一致率显著低于其他（如 mac 快捷键类），
   优先怀疑该校准数据覆盖不足（校准集与评估集的平台构成见 `README.md`）。

## 7. 非核心（可选）辅助指标

- **Thought 相似度**：free text 不做一致性判定；可用 embedding 余弦相似度或 ROUGE-L
  观察量化是否改变推理风格（仅诊断用，不进决策）。
- **Summary 与 Action 的一致性**：Summary 描述与 Action 不符的比例（蒸馏数据固有噪声
  的延续性检查）。
- **vs 人工 GT**：`model_action == gt_action` 仅作绝对水平参考（实测基线很低 ~7.5%，
  因为 GT 与 BF16 本身就常不一致——这正说明评估必须以 BF16 为锚，不能以 GT 为锚）。
